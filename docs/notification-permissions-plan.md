# 알림 권한과 설정 UI 개발 계획

작성일: 2026-09-18. 상태: 구현 및 자동 검증 완료, iOS 실기기 검증 대기.

상태 소유권과 선행 이전 순서는 [Zustand 기반 앱 전체 상태 관리 계획](zustand-state-management-plan.md)을 따른다. 이 문서는 알림의 사용자 흐름과 환경별 동작을 구체화하며, Zustand 이전 결과를 재사용한다.

기준 문서는 [제품 스펙](product-spec.md), [제품 용어](../CONTEXT.md), [프로젝트 구조](project-structure.md), [디자인 토큰](design-tokens.md)이다. 이 문서는 동작과 검증 기준을 정한다. 구현·검증 결과는 마지막 절과 진행 기록에 구분한다.

## 1. 목표와 범위

- 앱을 열면 시작 시점에 알림 제공 여부와 권한을 한 번 확인한다. 권한이 필요하면 앱의 안내 팝업을 먼저 보여주고, 사용자가 확인을 눌렀을 때 OS 권한 요청을 시작한다.
- 설정에서 O/X 라디오로 알림 사용 여부를 선택하고, X → O 선택에 권한 요청을 연결한다.
- 사용자 선택, 실제 기기 권한, 예약 처리 결과를 구분하여 현재 가능한 동작을 정확하게 보여준다.
- 환경별 API와 제약은 기존 `platform/notifications` 경계 안에서 처리한다. 타이머 계산과 레일에는 플랫폼 분기를 추가하지 않는다.
- 기존 한 번의 제스처 시작, `endAt` 기준 카운트다운, 완료 목록 병합, 확인할 때까지 반복되는 브라우저 알림음을 유지한다.

### 환경별 구현 범위

| 환경                           | 이번 구현                                                                       | 화면 안내                                        |
| ------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------ |
| Capacitor iOS 앱               | 시작 시 권한 조회와 안내 팝업, O/X 선택, 예약·취소, 복귀 시 재확인, 테스트 알림 | 실제 기기 권한과 사용 여부 표시                  |
| 모바일·데스크톱 웹 및 현재 PWA | 기존 브라우저 알림음 유지, 시스템 알림 미제공 상태 표시                         | `현재 웹 버전에서는 기기 알림을 제공하지 않아요` |
| Android                        | 이번 구현 대상에서 제외                                                         | 출시 작업에서 권한과 예약 제약을 별도로 검증     |

웹은 현재 제품 스펙의 MVP 범위를 유지한다. 브라우저에 `Notification` API가 있다는 이유만으로 이 서비스가 시스템 알림을 제공한다고 표시하거나 권한만 요청하지 않는다. 웹 시스템 알림과 service worker·Web Push는 별도 후속 범위다. 모바일 웹 알림에는 데스크톱의 생성자 호출과 다른 구현이 필요하다. [MDN 안내](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)

공유 상태는 앱 전체 계획에 따라 Zustand로 이전한다. 알림만을 위한 별도 store나 범용 권한 관리 프레임워크, 레일 XState 확장, Android 프로젝트 생성은 포함하지 않는다. 잠금·백그라운드·무음 상태의 실제 알림 전달은 권한 허용만으로 보장하지 않으며 iOS 실기기 검증 결과를 별도로 기록한다.

## 2. 구현 전 코드에서 확인한 사항

| 위치                                  | 현재 동작                                             | 변경 방향                                                         |
| ------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------- |
| `platform/notifications/index.ts`     | 웹·Capacitor 구현 선택                                | 환경 선택 지점 유지                                               |
| `notificationPort.ts`                 | `ensurePermission(): Promise<boolean>`                | 조회와 요청을 분리하고 상태를 보존                                |
| `browserNotifications.ts`             | 권한은 항상 `true`, 예약·취소는 아무 작업도 하지 않음 | 서비스의 웹 알림 미제공 상태를 반환                               |
| `capacitorNotifications.ts`           | 권한 확인·요청, 종료 시각 예약, ID별 취소             | 기존 API를 재사용하고 조회·요청·복귀 구독을 분리                  |
| `syncNotifications.ts`                | 예약 처리 중 권한 요청, ID별 직렬 처리                | 명시적 요청 제거, 사용 여부와 최신 권한에 따라 동기화             |
| `useTimerNotifications.ts`            | 예약, 반복 알림음, 일반 실패 여부 관리                | 상태는 Zustand 알림 영역, 외부 작업은 앱 실행 계층으로 이전       |
| `useTimers.ts`                        | 알림 훅 호출과 오디오 활성화까지 포함                 | 타이머 원본·시각은 Zustand, Worker·오디오는 앱 실행 계층으로 이전 |
| `useSettings.ts`, `timerStorage.ts`   | 시간 범위·테마만 저장·복구                            | 알림 사용 선택을 기존 저장·복구 방식에 추가                       |
| `SettingsPanel.tsx`, `AppNotices.tsx` | 알림 설정 없음, 일반 재시도 안내                      | O/X 항목, 기기 권한과 구체적인 복구 안내 추가                     |

2026-09-18 확인한 설치 버전은 `@capacitor/local-notifications` 8.2.0이다. `checkPermissions`, `requestPermissions`, `getPending`은 설치된 패키지에 있다. 현재 구현에는 `@capacitor/app` 8.1.1을 설치하고 iOS 프로젝트에 동기화했다. 최신 문서의 8.3 이상 전용 동작을 현재 구현에 있다고 가정하지 않는다.

## 3. 설정 화면과 상호작용

색상 테마 아래, 사용 방법 위에 알림 섹션을 둔다. 이 문서의 `기기 알림`은 제품 용어의 네이티브 알림을 화면에서 부르는 이름이다.

```text
알림
기기 알림 사용       [ O 사용 ] [ X 사용 안 함 ]
기기 권한: 허용됨
[테스트 알림 보내기]

앱 내부 알림음       활성화됨
[소리 테스트]
```

라디오의 선택 표시는 현재 사용 가능한 상태에서 계산한다. 사용자가 O를 눌렀다는 이유만으로 성공 표시를 확정하지 않는다.

| 상황·조작              | 선택 표시와 처리                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------- |
| 최초 조회 중           | `확인 중` 표시. O/X를 확정하지 않고 조작 잠금                                           |
| X → O, 권한 미요청     | 요청 중 표시 → 허용 시 O, 거부·닫기·오류 시 X로 복귀하고 이유 안내                      |
| X → O, 이미 허용       | 추가 권한 창 없이 사용을 켜고 진행 중 타이머 예약                                       |
| X → O, 차단됨          | 상태를 재확인하고 X 유지. 다시 띄울 수 없는 권한 창을 반복 요청하지 않고 설정 변경 안내 |
| O → X                  | 사용자 선택을 끄고 새 예약 차단, 기존 예약 취소. OS 권한 자체는 유지                    |
| X이며 OS 권한은 허용됨 | `기기 권한: 허용됨 · 앱에서 사용 안 함` 표시                                            |
| 조회 실패              | `권한을 확인하지 못했어요`와 다시 확인 제공. 거부나 미지원으로 처리하지 않음            |
| 예약·취소 실패         | 권한 표시를 바꾸지 않고 해당 작업의 오류·재시도 제공                                    |
| 웹 미제공              | O 선택 비활성화와 이유 표시. 기기 권한을 `차단됨`으로 표시하지 않음                     |

- O/X 기호와 `사용`·`사용 안 함` 텍스트를 함께 표시한다. `fieldset`, `legend`, 실제 `input type="radio"`를 사용한다.
- 클릭·터치·키보드 선택은 같은 핸들러를 사용한다. 요청 중 재입력을 막고 상태 메시지는 `aria-live="polite"`로 알린다. 라디오 선택 복귀와 초점 유지를 함께 확인한다.
- 조작 영역은 최소 44 × 44 CSS px로 두고 모든 테마의 대비, 초점 표시, 하단 안전 영역과 200% 글자 확대를 검증한다.
- 토큰의 색상·간격·모션을 재사용한다. 상태 전환은 짧은 opacity/transform 효과로 표현하고 동작 줄이기 설정을 따른다.
- 차단 상태에는 기기 설정 변경 방법과 `다시 확인`을 제공한다. 설정 앱 직접 열기는 설치된 API로 가능한지 확인한 뒤 지원 환경에서만 제공한다. 버튼만을 위해 별도 플러그인을 추가하는 것은 이번 필수 범위가 아니다.
- 앱 내부 알림음은 기존 `audioReady`를 기준으로 표시한다. `알림음 켜기`와 한 번의 `소리 테스트`를 제공하며 기기 알림 O/X와 독립적으로 동작한다. 테스트 때문에 반복 알림의 주기를 재시작하거나 완료 목록을 변경하지 않는다.
- 테스트 알림은 O 상태에서만 명시적 버튼 조작으로 보낸다. 어댑터 내부의 테스트 식별자를 사용하여 실제 타이머 저장·완료 목록에 포함하지 않는다. API 호출 성공은 `테스트 알림을 요청했어요`로 안내하고 실제 수신을 확인했다고 표현하지 않는다.

### 앱 시작 시 권한 안내 팝업

```text
앱 실행 → 알림 제공 여부·기기 권한 확인
  ├─ 이미 허용됨 → 안내 없이 기존 사용 선택 반영
  ├─ 미요청 + 앱에서 사용 중지하지 않음 → 앱의 권한 안내 팝업
  │    ├─ 확인 → 공통 권한 요청 → OS 권한 창 → 결과 반영
  │    └─ 나중에 → 이번 실행에서는 안내 종료, 타이머 사용 계속
  └─ 차단됨·사용 중지·미제공·조회 실패 → 상태에 맞는 안내·복구 제공
```

- 제목은 `타이머 완료 알림을 받을까요?`, 설명은 `완료 시 기기 알림을 받을 수 있도록 알림 권한을 허용해 주세요. 설정에서 언제든 사용 여부를 바꿀 수 있어요.`를 기준으로 작성한다.
- 버튼은 `확인`과 `나중에`를 제공한다. 확인 버튼의 설명에 기기 권한 창이 이어서 열린다는 점을 명시한다. 앱의 안내 팝업과 OS 권한 창은 별개다.
- 앱을 여는 즉시 조회를 시작하되, 사용자 설정 읽기가 끝나기 전에는 팝업 노출을 결정하지 않는다. 사용자가 이전에 X를 선택했거나 권한을 거부했다면 자동 안내 팝업을 다시 띄우지 않는다. 차단 상태의 변경 방법은 설정에서 제공한다.
- 이미 허용된 사용자와 기기 알림 미제공 환경에는 불필요한 권한 안내를 띄우지 않는다. 웹은 제공 여부 확인 후 기존 앱 내부 알림음 흐름을 유지한다.
- `나중에`, Escape, 뒤로 가기로 안내만 닫으면 기존 사용 선택을 바꾸지 않는다. 미선택인 `null`은 유지하여 다음 앱 실행 때 다시 안내할 수 있게 한다. 같은 실행 중 화면 재진입·복귀·재렌더링으로 자동 팝업을 반복하지 않는다.
- `dialog`로 제목·설명을 연결하고 초점 제한·닫힌 뒤 초점 복귀를 제공한다. 앱 시작 시 돌아갈 초점이 없으면 시작 핀으로 보낸다. 팝업이 열린 동안에도 진행 중 타이머의 시간 계산을 유지한다.
- 저장된 완료 타이머의 완료 알림을 우선한다. 레일이 `idle`이고 설정·완료 알림이 닫혀 있을 때만 권한 안내를 표시한다. 생성·편집 드래그, 타이머 액션, 시간 조정 중에는 보류하고, 드롭·취소·메뉴 닫기·조정 종료 후 최신 권한과 사용자 선택을 다시 확인하여 안내한다. 보류는 안내를 처리한 것으로 기록하지 않는다. 권한 안내 중 타이머가 완료되어도 완료 알림을 우선하고, 확인 후 미처리 안내의 조건을 다시 판단한다.
- `App`에서 생성한 동일한 레일 actor 참조를 `TimerRail`과 권한 안내에 전달한다. 권한 안내는 `idle` 여부만 `useSelector`로 구독하고 설정·완료·권한 상태는 Zustand에서 읽는다. `idle` 여부를 store에 복사하거나 `getSnapshot()` 조회만으로 화면 갱신을 기대하지 않는다. 드래그 좌표가 바뀌어도 안내의 boolean 구독값은 유지한다.
- 설정의 O 선택과 팝업의 확인은 동일한 공통 요청 동작을 사용한다. 확인 전에는 OS 요청을 호출하지 않고, 확인 시 요청을 사용자 클릭에서 직접 시작한다. 요청 중 재입력을 막고 결과를 설정의 O/X와 안내 문구에 함께 반영한다.

## 4. 상태의 기준과 저장 이전

| 값                                        | 기준·소유 위치                                       | 저장 여부                                      |
| ----------------------------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| `notificationPreference: null \| boolean` | `AppSettings`와 Zustand 설정 영역                    | 저장                                           |
| 알림 제공 여부                            | 어댑터 결과를 Zustand 알림 영역에서 보관             | 저장하지 않음                                  |
| 기기 권한 `prompt / granted / denied`     | OS 응답을 Zustand 알림 영역에서 보관                 | 저장하지 않음                                  |
| 조회·요청 진행, 조회 오류                 | Zustand 알림 영역                                    | 저장하지 않음                                  |
| 시작 조회·안내 처리 여부                  | Zustand 알림 영역의 실행 단위 상태                   | 저장하지 않음. 복귀·재렌더링과 새 실행을 구분  |
| 예약·취소 실패                            | 작업 큐는 동기화 모듈, 화면 오류는 Zustand 알림 영역 | 저장하지 않음. 재시작 시 실제 예약 조회로 복구 |
| O/X 선택 표시                             | 제공 여부·권한·사용자 선택에서 계산                  | 별도 저장하지 않음                             |

`null`은 아직 사용 여부를 선택하지 않은 기존 사용자와 신규 사용자를 뜻한다. `false`는 명시적으로 사용하지 않겠다는 선택 또는 권한 요청이 허용으로 끝나지 않은 상태, `true`는 사용하겠다는 선택이다. 최초 상태를 단순 `false`로 두면 기존 네이티브 알림을 끄거나 시작 시 권한 안내 대상을 구분하지 못하므로 세 값을 사용한다.

- O 조건: 기기 알림 제공 + 확인된 `granted` + 사용자 선택이 `false`가 아님. 기존 사용자에게 이미 권한이 있으면 기존 알림 동작을 유지한다. 예약 실패는 별도 경고이며 O를 전달 성공 표시로 사용하지 않는다.
- 권한 조회가 미완료·실패면 O/X를 단정하지 않고 확인 상태를 표시한다. 새 예약은 보류한다. 이 상태를 명시적 X나 빈 예약 목표 목록으로 변환하여 기존 예약을 일괄 취소하지 않는다. 변경 없는 유효 예약은 유지하며, 사용자 조기 종료·완료 확인·X 선택 또는 종료 시각 변경으로 무효가 된 예약의 취소는 별도로 처리한다.
- 외부 설정에서 권한이 거부되면 X를 표시하되 기존 사용자 선택은 유지한다. 다시 허용되면 기존 선택이 `true` 또는 `null`인 경우만 O로 돌아간다. 명시적인 `false`를 자동으로 켜지 않는다.
- 신규 필드가 없는 정상 설정은 `null`로 이전하면서 기존 시간 범위·테마를 보존한다. 필드가 있으면 boolean 또는 null만 수용하며 잘못된 값은 알림에 한해 `false`로 보정한다. JSON 읽기 실패 등 기존 저장소 실패 처리 규칙은 유지한다.
- Zustand 설정 영역으로 이전한 수정 필드 추적에도 신규 필드를 포함하여 읽기 실패 중 사용자가 선택한 값을 복구 시 보존한다.
- 읽기에 실패한 설정을 `null` 기본값으로 오인하여 초기 안내 팝업을 띄우지 않는다. 권한 조회 자체는 가능하지만 안내 대상 판단은 저장 복구 뒤에 한다. 읽기 성공 여부는 Zustand의 저장 복구 상태에서 읽는다. 쓰기 실패와 읽기 미완료를 구분한다.
- 저장 실패 시 메모리의 선택은 동작하고 저장 재시도를 제공한다. X로 바꾼 후 저장에 실패하면 예약 취소를 계속 시도하되, 앱 재실행 후 이전 선택이 복원될 수 있음을 안내한다.
- 타이머 저장소를 읽지 못한 상태는 빈 타이머 목록이 아니다. 이를 근거로 기존 기기 예약을 일괄 제거하지 않는다. 단, 사용자의 명시적 X 선택은 기존 예약 취소를 실행한다.

## 5. 권한 요청과 예약의 경계

### 공통 연결 구조

```text
AppStateProvider
  ├─ Zustand: 타이머·설정·권한·앱 화면 상태
  └─ appRuntime: 담당 모듈 연결·해제, 공개 AppActions 조립
       └─ notificationRuntime: 권한 조회·요청·store 반영, 알림 연결
            ├─ syncNotifications: ID별 예약·취소, 공통 경로를 통한 예약 가능 여부 확인
            └─ NotificationPort
                 ├─ 웹: 미제공 상태, 브라우저 복귀 감지
                 └─ iOS: Capacitor 권한·예약·취소·복귀 감지
시작 안내 팝업 / SettingsPanel / AppNotices ← 상태 selector와 공개 AppActions
```

- 앱 루트에서 알림 실행 모듈을 한 번 연결한다. 메인·설정·완료 화면은 같은 Zustand의 필요한 상태만 구독한다. 설정 화면을 열 때 별도 권한 상태나 예약 실행자를 만들지 않는다.
- 화면은 공개 `AppActions`의 요청·사용 중지·재확인·안내 종료·테스트 동작만 호출한다. 원본 store와 내부 권한 반영 액션은 화면용 타입·export에 노출하지 않는다. `appRuntime.ts`는 참조 조립과 연결만 맡고 권한 전환 규칙은 `notificationRuntime.ts`에 둔다.
- 기존 `useTimers`의 타이머 상태는 Zustand로, 알림 연결은 앱 실행 계층으로 이전한다. 사용자 시작 콜백은 오디오 준비와 타이머 생성만 연결한다. 권한 요청은 시작 안내의 확인 또는 설정의 O 선택에서 수행하며 타이머 생성·편집에서는 요청하지 않는다. 드래그, 탭 후 시간 조정, 키보드 생성이 모두 같은 시작 콜백을 사용해야 한다.
- `NotificationPort`는 `ensurePermission`을 `checkPermission`과 `requestPermission`으로 나눈다. 제공 여부를 권한 거부와 구분해서 반환하며 조회 오류는 실패로 전달한다.
- 기존 `scheduleTimer`, `cancelTimer`, `onNotificationAction`을 유지한다. 실제 예약 조회, 테스트 알림, 복귀 구독은 각각 필요한 최소 메서드만 추가하고 플러그인 객체를 화면에 노출하지 않는다.
- 어댑터 내부에서 `LocalNotifications` 상태를 공통 값으로 변환한다. UI와 도메인은 `Capacitor`, `Notification`, OS별 권한 문자열을 직접 참조하지 않는다.
- `notificationRuntime`이 `NotificationPort`의 권한 조회·요청과 store 반영을 전담한다. 초기 조회·복귀·설정 재확인·예약 전 재확인은 같은 조회 경로를 사용한다. 진행 중 조회 공유, 명시적 요청과의 순서 조정, 오래된 응답 무시는 이 모듈 한곳에서 처리한다.
- `syncNotifications`에는 예약·취소 기능과 `notificationRuntime`의 예약 가능 여부 확인 콜백만 전달한다. 동기화 모듈이 권한 API를 직접 조회·요청하거나 별도 권한 캐시를 보관하지 않는다. 확인 콜백은 권한 조회 결과를 store에 반영하고 최신 사용자 선택을 확인한다. 동기화 모듈은 대기가 끝난 뒤 최신 대상과 종료 시각을 다시 검증한다. 권한 거부는 정상적인 예약 보류 사유이며 일반 플러그인 오류로 던지지 않는다. [Capacitor 권한 API](https://capacitorjs.com/docs/apis/local-notifications#checkpermissions)
- 예약 전 조회에서 거부가 확인되면 설정 화면도 같은 결과로 X를 표시한다. 조회 오류는 거부로 바꾸지 않고 확인 실패를 표시하며 새 예약을 보류한다. 조회 결과를 store에 반영하는 과정에서 같은 예약을 중복 생성하거나, 조회와 예약이 서로의 완료를 기다리는 순환 대기를 만들지 않는다.

### 앱 시작과 복귀

1. 매 새 앱 인스턴스에서 `notificationRuntime`의 초기 조회를 한 번 시작한다. 메인 화면은 즉시 표시하고 타이머 복원을 병행한다. 초기 조회와 시작 직후 focus·활성화 이벤트가 겹치면 공통 조회 경로의 진행 중 작업을 공유한다. 같은 인스턴스의 `stop → start`는 구독만 다시 연결하며 저장값을 재복원하거나 사용자 선택·실패 상태·안내 처리 여부를 초기화하지 않는다. React StrictMode의 effect 재실행도 검증한다.
2. 제공 환경에서 권한이 미요청이고 사용자 선택이 `false`가 아니면 안내 대상으로 둔다. 설정 읽기가 성공했고 레일이 `idle`이며 설정·완료 알림이 닫혀 있을 때 앱의 안내 팝업을 연다. 앱 실행·설정 진입·복귀·타이머 복원·일반 재시도 자체는 OS 권한 요청을 실행하지 않는다.
3. 안내 팝업의 확인 또는 설정의 O 선택에서 공통 요청을 실행한다. 미허용 상태에서 요청을 시작할 때 사용자 선택을 `false`로 기록하고, 허용되면 `true`로 전환한다. OS 창 거부·닫기·요청 실패 시 X를 유지하고 이유와 재시도 방법을 알린다. 안내의 `나중에`는 OS 요청을 실행하지 않으며 이 선택 저장 규칙의 대상이 아니다.
4. 이미 허용된 사용자는 추가 안내·요청 없이 기존 선택을 반영한다. 사용 중지·차단·미제공 상태와 조회 실패에서도 타이머 생성과 앱 내부 알림음은 유지한다. 타이머의 `endAt`은 사용자 확정 시각에서 계산하며 조회·안내·권한 대기 시간 때문에 변경하지 않는다.
5. 복귀 구독은 웹의 focus·visibility와 iOS의 활성화 이벤트를 어댑터 안에서 처리한다. iOS에는 공식 `@capacitor/app`의 활성화 구독만 도입하고 구독 해제를 보장한다. 해당 API는 네이티브 앱 활성화를 제공한다. [Capacitor App 문서](https://capacitorjs.com/docs/apis/app#addlistenerappstatechange-)
6. 복귀는 상태와 예약 재확인만 수행하며 초기 안내 절차를 다시 시작하지 않는다. 여러 복귀 이벤트를 중복 처리하지 않고, 먼저 시작한 오래된 조회 결과가 최신 요청 결과를 덮어쓰지 않게 한다. OS 권한 창으로 인한 비활성화·활성화도 이 규칙을 따른다.
7. 설정 재시도 등으로 이미 권한 요청이 진행 중이면 초기 안내를 추가로 띄우지 않는다. 안내 표시 여부를 OS 권한이나 영구 사용자 선택과 같은 값으로 저장하지 않는다.
8. 웹 시스템 알림을 후속 구현할 때도 확인 버튼 등 사용자 행동에서 직접 요청하는 경계를 유지한다. 브라우저 요청을 React effect나 비동기 예약 작업 뒤에 숨기지 않는다. [MDN 권한 요청 안내](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static)

### 예약 보존·취소·교체의 처리 순서

현재 `syncNotifications`의 일괄 `취소 → 권한 확인 → 예약` 순서는 변경한다. 권한 조회 실패를 이유로 유효 예약이 먼저 삭제되지 않도록 아래 작업을 구분한다. ID별 직렬 처리와 최신 목표 검증은 유지한다.

| 상황                                          | 처리 순서와 실패 기준                                                                                                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기존 예약의 ID·종료 시각이 최신 타이머와 일치 | 단순 권한 재확인·재시도로 취소하거나 재예약하지 않는다. 조회 실패에도 예약을 유지하고 권한 확인 오류만 표시한다.                                                                                                    |
| 새 예약이 필요함                              | 공통 권한 확인 → 최신 사용자 선택·대상·종료 시각 검증 → 허용 시 예약. 미확인·실패·거부이면 보류한다.                                                                                                                |
| 조기 종료·완료 확인·명시적 X 선택             | 권한 확인 성공을 조건으로 삼지 않고 해당 예약을 취소한다. 취소 실패는 재시도 대상으로 남기고 새 예약은 막는다.                                                                                                      |
| 시간 조정으로 종료 시각이 바뀜                | 권한 응답을 기다리지 않고 이전 예약 취소 → 공통 권한 확인 → 최신 의도 검증 → 취소 성공과 예약 허용을 확인한 뒤 최신 종료 시각으로 예약한다. 조회 실패·거부여도 이미 무효인 이전 예약은 취소하고 새 예약은 보류한다. |

- 교체 도중 취소가 실패하면 새 예약을 실행하지 않는다. 취소 후 예약이 실패하면 이전 종료 시각으로 되돌리지 않고 최신 목표의 재시도를 남긴다. 조회 실패로 보류한 새 예약도 권한 재확인 성공·사용 켜기·명시적 재시도에서 다시 처리하며 목표가 같다는 이유만으로 누락하지 않는다.
- 각 비동기 작업 뒤 최신 의도를 다시 검증한다. 대기 중 조기 종료·X 선택은 취소 경로로, 추가 시간 조정은 마지막 종료 시각의 교체 경로로 처리한다. 진행 중 예약이 뒤늦게 완료되는 경우의 취소도 같은 ID 대기열을 사용한다.
- 예약 보존은 실제 예약이 최신 타이머와 일치하는 경우에 적용한다. 이전 종료 시각의 예약을 없애는 이유는 사용자 시간 조정이며 권한 조회 오류가 아니다. 새 예약 보류·취소 실패·예약 실패를 성공으로 표시하지 않고 해당 복구 동작을 제공한다.

### 취소·복구와 경쟁 조건

- O가 되면 현재 시각보다 `endAt`이 큰 최신 타이머만 예약한다. 권한을 기다리는 동안 완료·삭제된 타이머는 예약하지 않고 조정된 타이머는 마지막 종료 시각만 사용한다.
- X 선택은 새 예약을 즉시 막는다. 이미 진행 중인 예약이 늦게 완료되면 같은 ID의 취소를 이어서 수행한다. 현재 ID별 직렬 처리와 삭제 후 취소 실패 재시도 규칙을 유지한다.
- X인데 취소에 실패하면 `일부 예약 알림을 취소하지 못했어요`와 재시도를 표시한다. 새 예약은 계속 막고 앱 내부 타이머는 유지한다. X를 모든 예약 취소 성공으로 오해하게 만들지 않는다.
- 앱 재시작 시 메모리의 `desired` 목록은 비어 있다. 단순히 빈 배열을 동기화하는 것으로는 이전 기기 예약을 제거할 수 없다. `getPending`으로 이 앱의 타이머 알림을 조회하고 저장된 선택·타이머와 대조한다.
- 실제 예약의 `extra.timerId` 등 소유 표식을 확인하여 남은 예약만 정리한다. 다른 용도의 알림을 무조건 취소하지 않는다. 테스트 알림도 전용 표식으로 구분한다.
- 시작·복귀 때의 예약 조회와 새 타이머의 생성·수정·X 선택이 경합해도 최신 의도를 사용한다. 조회 실패 시 재시도를 제공하며 확인하지 못한 기존 예약을 정상 처리했다고 표시하지 않는다.
- 설정 화면을 닫아도 앱 실행 계층이 요청을 마무리하고 결과를 Zustand에 반영한다. 앱이 종료되어 요청 결과를 받지 못했으면 다음 실행에서 실제 권한을 다시 조회한다.

## 7. 검증 계획

### 자동화할 핵심 시나리오

- [ ] 권한 조회는 OS 요청을 호출하지 않으며 허용·거부·미요청·미제공·조회 실패를 구분한다.
- [ ] 앱 시작 시 타이머 생성 없이 초기 조회를 실행한다. 시작 시 활성화 이벤트·재렌더링·StrictMode가 겹쳐도 초기 조회와 안내가 중복되지 않는다.
- [ ] 저장 실패 중 알림 사용 선택을 변경한 뒤 같은 인스턴스를 재연결해도 메모리 선택·수정 필드·실패 상태가 유지된다. 저장 복원은 최초 시작 또는 읽기 실패의 명시적 재시도에서만 수행한다.
- [ ] 미요청 사용자에게 안내 팝업을 보여주고 확인 전 OS 요청 호출은 0회다. 확인 후 공통 요청이 정확히 1회 실행된다. 이미 허용·차단·명시적 X·미제공·설정 읽기 실패에서는 자동 팝업을 띄우지 않는다.
- [ ] 안내의 나중에·Escape·뒤로 가기는 OS 요청을 호출하지 않는다. 미선택 값을 유지하고 같은 실행 중 재노출하지 않으며 다음 실행의 초기 조회·안내는 다시 가능하다.
- [ ] 권한 요청은 안내의 확인과 설정의 O 선택에서만 실행한다. 첫 타이머를 포함한 생성·복원·편집·일반 재시도에서는 요청하지 않는다. 두 진입점의 중복 조작도 단일 요청으로 처리한다.
- [ ] 완료 알림·설정·시간 조정과 초기 안내를 겹쳐 띄우지 않는다. 닫힌 뒤 권한·사용 선택을 재확인하고 필요한 경우에만 안내하며 초점을 적절하게 복원한다.
- [ ] 생성·편집 드래그 중 초기 권한 조회가 끝나도 팝업 없이 드롭 또는 취소까지 조작을 마칠 수 있다. 타이머 액션·시간 조정에서도 보류하고, 같은 actor의 `idle` 복귀 후 최신 조건으로 안내한다. 안내 중 완료가 발생하면 완료 알림을 우선한다. 미리보기의 드래그 이동만으로 권한 안내의 `idle` 구독값이 바뀌지 않는다.
- [ ] O 선택 → 허용 시 O, 거부·닫기·실패 시 X 복귀. 허용 상태에서의 O 선택에는 요청 창이 없다.
- [ ] X 선택 후 기존 예약을 취소하고 이후 생성 타이머를 예약하지 않는다. 늦게 완료되는 예약도 취소한다. 취소 실패는 삭제된 타이머와 재시작 뒤에도 복구할 수 있다.
- [ ] 요청 중 삭제·완료·시간 조정, 빠른 O/X 변경, 늦은 조회 응답에서 최신 선택과 종료 시각만 반영한다.
- [ ] 외부 권한 변경 후 복귀하면 표시·예약이 갱신된다. 명시적으로 끈 사용자의 설정은 자동으로 켜지지 않는다.
- [ ] 예약 전 권한 재확인에서 거부·조회 오류가 확인되면 store·설정 표시도 같은 결과를 반영한다. 초기 조회·복귀·명시적 요청과 경합해도 오래된 결과가 최신 상태를 덮지 않고 예약 중복·순환 대기가 없다.
- [ ] 최신 종료 시각으로 이미 예약된 타이머의 단순 권한 재조회가 실패하면 취소·예약 호출은 0회이고 기존 예약은 유지된다. 같은 조회 실패 상태에서도 조기 종료·완료 확인·X 선택은 해당 예약을 취소한다.
- [ ] 시간 조정 후 조회 실패·거부에는 이전 종료 시각의 예약을 취소하고 새 예약은 보류한다. 권한 대기가 이전 예약 취소를 막지 않으며, 조회 성공 시 취소 성공 → 최신 의도 확인 → 최신 시각 예약 순서를 지키고, 취소 실패 시 교체를 진행하지 않는다. 예약 실패·조회 실패로 미예약 상태가 된 목표는 재시도 시 최신 시각으로 예약하며 이전 시각을 복원하지 않는다. 대기 중 추가 조정·X 선택에도 같은 규칙을 적용한다.
- [ ] 화면용 타입·export는 내부 권한 반영 액션과 원본 store를 제공하지 않는다. 시작 안내와 설정은 동일한 공개 요청 동작을 사용한다.
- [ ] 과거 시간 범위·테마만 있는 저장값과 기존 허용 사용자의 예약을 보존한다. 읽기 실패를 빈 저장소로 취급하지 않으며 새 필드의 저장 실패·재시도·재실행을 검사한다.
- [ ] 기기 알림 X·권한 거부·웹 미제공에서도 타이머 생성, 1초 표시, 반복 알림음, 완료 병합·확인이 유지된다.
- [ ] 테스트 알림·소리 테스트가 실제 타이머와 완료 목록을 변경하지 않으며 반복 알림음 주기를 깨뜨리지 않는다.
- [ ] 라디오의 키보드 이동·선택, 요청 후 초점, 스크린리더용 상태 문구, 네 테마·200% 확대·모바일 하단 접근성을 확인한다.

어댑터·동기화 단위 검사는 기존 Vitest 테스트에 미해결 Promise와 실패 응답을 넣어 경합을 재현한다. 브라우저 검사는 실제 Zustand와 앱 실행 계층부터 설정 화면까지 연결하여 허용·거부·재시도·복귀를 확인한다. 테스트용 어댑터 교체는 기존 경계에서 수행하고 배포 앱에 테스트 전역 객체나 설정 플래그를 추가하지 않는다. 웹 실제 실행에서는 미제공 상태와 오디오 흐름도 별도로 검사한다.

### 실행 순서와 완료 판정

1. 단계별로 변경한 동작의 테스트를 먼저 확인한다.
2. Node 24에서 `npm run verify`, 이어서 `npm run verify:browser`를 실행한다. 기존 회귀 검사를 제거하거나 기대값을 느슨하게 바꿔 통과시키지 않는다.
3. 대표 오류를 임시로 주입하여 새 검사가 실제 실패하는지 확인한다. 대상은 조회 중 권한 요청, X 이후 지연 예약, 권한 거부 후 O 표시 중 최소 두 가지다.
4. 코드 리뷰에서 UI·타이머 도메인의 플랫폼 API 유입, 중복 상태, 구독 누수, 과거 예약 잔존, 저장 실패 시 데이터 손실을 확인하고 수정 후 관련 검사를 다시 실행한다.
5. iOS 실기기에서 최초 실행의 조회 → 앱 안내 → 확인 → OS 권한 창, 나중에·허용·거부, 설정의 O/X, 외부 권한 변경 후 복귀, 앱 종료·재실행 후 예약, 잠금·백그라운드·무음·집중 모드, 실제 알림 소리와 알림 탭 복귀를 검사한다. 전경의 시스템 알림과 반복 알림음이 중복 재생되는지도 확인한다.
6. 실기기 기록에는 기기·OS·앱 빌드, 조건, 예상·실제 결과를 남긴다. 에뮬레이션, 플러그인 mock, API 호출 성공을 실제 알림 전달 확인으로 대체하지 않는다.

코드·자동 검사가 끝나도 기기 검증이 남았다면 `구현 완료 / 실기기 검증 미완료`로 보고한다. 실기기 미확인 항목은 완료 체크하지 않는다.

## 8. 구현 결과 (2026-09-18)

- 앱 시작 조회·안내·확인 후 요청, 설정 O/X와 재확인·테스트 알림·소리 테스트를 연결했다. 웹은 기기 알림 미제공을 표시하며 시스템 권한을 요청하지 않는다.
- 권한 결과와 사용자 선택은 별도 값이다. 현재 실행의 선택은 저장 실패에도 적용되며, 읽기에 실패한 기본값은 동의로 간주하지 않는다.
- 네이티브 실제 예약 조회와 권한 조회를 병행한다. 첫 예약 목록 반영 뒤 새 예약을 허용하고, 이미 유효한 같은 예약은 유지한다. 취소는 권한 대기와 독립적이다.
- 예약 목록 응답의 유효성 검사는 실제 OS 작업 변경 이력을 사용한다. 조회 도중 X를 선택하거나 타이머를 삭제해도 응답으로 발견한 기존 예약을 취소한다.
- 자동 검사는 실제 store·실행 계층·화면을 연결하고 외부 어댑터만 대체한다. `tests/fixtures/permissions.html`은 Vite 개발 서버의 검사용 진입점이며 배포 빌드에 포함되지 않는다.
- iOS 시스템 팝업·실제 전달·잠금·백그라운드·무음·집중 모드·VoiceOver는 실기기 미검증이다. 체크리스트는 이 항목까지 모두 완료한 것으로 간주하지 않는다.
