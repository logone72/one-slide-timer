# Zustand 기반 앱 전체 상태 관리 적용 계획

작성일: 2026-09-18. 상태: 구현 및 자동 검증 완료, iOS 실기기 검증 대기.

## 1. 목적과 결정

Zustand를 앱의 공유 상태를 소유하는 기본 시스템으로 도입한다. 타이머, 설정, 앱 화면, 저장 복구 상태, 알림·권한 상태 전체를 대상으로 한다. 목적은 각 값의 소유자와 변경 경로를 명확히 하고, React 렌더링과 외부 작업의 수명을 분리하는 것이다.

- 앱 인스턴스마다 **하나의 Zustand vanilla store**를 만든다. 타이머·설정·알림·화면의 네 영역으로 코드 책임을 나누되, 별도 store 사이의 동기화는 만들지 않는다.
- store는 상태와 동기적인 변경 액션을 소유한다. 저장소, Worker, 알림 API, 오디오, DOM 변경은 앱 실행 계층에서 수행한다.
- XState는 기존 레일 상호작용의 소유자로 유지한다. 입력 중 값과 DOM 측정·애니메이션 자원은 컴포넌트에 둔다. 모든 상태를 검토하되 같은 값을 여러 상태 시스템에 저장하지 않는다.
- 기존 저장 형식과 복구 규칙을 유지하기 위해 최초 도입에는 Zustand `persist`를 사용하지 않는다. 상태 관리 이전과 저장 형식 변경을 한 번에 진행하지 않는다.
- 새 의존성은 Zustand로 한정한다. 알림 기능에 필요한 `@capacitor/app`은 [알림 계획](notification-permissions-plan.md)의 별도 의존성이다. 범용 이벤트 버스, 자동 액션 생성기, Immer, 별도 상태관리 프레임워크는 추가하지 않는다.

Zustand의 `createStore`는 React 밖에서도 상태 조회·구독이 가능한 store를 만든다. 이 기능으로 앱 실행 계층과 UI가 동일한 인스턴스를 사용한다. [공식 API](https://zustand.docs.pmnd.rs/reference/apis/create-store)

이 문서가 **상태 소유권·이전 순서의 기준**이다. [알림 계획](notification-permissions-plan.md)은 초기 권한 안내, O/X 설정, 플랫폼별 동작의 제품 기준으로 함께 적용한다. [제품 스펙](product-spec.md), [용어](../CONTEXT.md), [프로젝트 구조](project-structure.md)의 현재 구현과 후속 계획을 구분한다.

## 2. 이전 전 구조에서 해결할 문제

- `useTimers`가 타이머 데이터, 저장, 시각 갱신, Worker 수명, 복귀 이벤트, 알림 연결을 함께 담당한다.
- `useSettings`가 설정 데이터, 복구용 수정 필드 추적, 테마 DOM 반영을 함께 담당한다.
- `useStoredState`가 React 상태와 저장 부작용을 결합한다. 훅을 다른 위치에서 다시 호출하면 독립적인 상태 소유자가 생긴다. 현재는 `App`에서 한 번만 호출하고 있어 실제 중복 저장이 발생한 것으로 판단하지 않는다.
- `App`이 매 시각 갱신을 구독하고 각 화면에 큰 반환 객체와 콜백을 전달한다. `AppNotices`는 구체적인 훅 반환 타입에 결합되어 있다.
- 예정된 초기 권한 안내와 설정 화면이 권한·복구 상태를 공유해야 한다. 기존 훅에 상태와 조건을 계속 추가하면 책임이 다시 섞일 수 있다.

이전의 성공 기준은 props 개수나 파일 수 자체가 아니라, 아래 상태 목록의 소유권과 테스트 가능한 변경 경로가 실제 코드에서 드러나는지다.

권한·오디오 스냅샷은 외부 상태를 화면에 전달하기 위한 값이다. 임의 액션으로 권한을 `granted`로 만들거나 오디오 활성화를 성공으로 가정하지 않는다. 읽기·요청 중·오류는 거부·미지원과 별도 상태로 표현한다.

## 4. 목표 구조와 의존 방향

```text
화면·XState → 공개 AppActions
  ├─ 범위·테마·화면 선택: 기존 동기 액션 참조
  └─ 타이머·권한·재시도: 담당 실행 모듈의 동작
       ├─ 내부 Zustand 변경 액션
       └─ 저장소 / Worker / 알림 어댑터 / 오디오

외부 이벤트 → 앱 실행 계층 → Zustand 변경 액션
Zustand → 필요한 값을 구독하는 화면
Zustand의 관련 값 변경 → 앱 실행 계층의 한정된 구독 → 외부 동작
```

### store 구성

- `createAppStore`는 초기 상태를 인자로 받아 독립적인 인스턴스를 만든다. 생성자·모듈 import 과정에서 저장소 읽기, 권한 요청, Worker 생성 등을 하지 않는다.
- 타이머·설정·알림은 각 상태와 액션을 같은 영역의 코드에 모은다. 화면 선택처럼 작은 상태는 조립 파일에 둔다. Zustand의 slice는 한 store를 구성하는 코드 분리 단위로만 사용한다. [공식 slice 안내](https://zustand.docs.pmnd.rs/learn/guides/slices-pattern)
- 배열·레코드는 불변 갱신하고 변경되지 않은 타이머 객체와 설정 필드의 참조를 보존한다. 시각 갱신만으로 타이머 배열을 새로 만들지 않는다.
- 화면은 `useAppStore(selector)`로 상태만 읽고 `useAppActions()`로 공개 동작만 얻는다. selector 입력은 상태 전용 `AppState` 타입으로 제한한다. 내부 변경 액션과 `setState`·`getState`를 포함한 원본 store는 화면에 노출하지 않는다.
- React Context는 앱 인스턴스의 고정된 store·사용자 동작 참조만 전달한다. 실제 상태 값을 Context에 복제하지 않는다. 테스트는 별도 store 인스턴스를 만들며 전역 singleton 초기화에 의존하지 않는다.
- 도메인 순수 함수는 Zustand·React·Capacitor를 import하지 않는다. 어댑터도 전역 store를 import하지 않고 결과·이벤트를 반환한다.

### 공개 동작과 내부 변경 액션

- `AppActions`를 UI·XState가 사용할 하나의 공개 호출 계약으로 둔다. 아래 동작과 알림 기능 단계에서 추가하는 동작만 노출한다. 화면이 내부 타이머 추가 액션을 호출하여 오디오 준비·기준 시각 갱신 등을 우회하지 못하게 한다.
- 복원 결과 반영, 저장 성공·실패 반영, 시각 갱신, 권한 결과 반영은 내부 액션이다. 이름뿐 아니라 타입과 export를 분리하고 화면용 훅이나 공개 진입점에서 다시 내보내지 않는다.
- 범위·테마·화면 선택처럼 외부 작업이 없는 공개 동작은 해당 동기 액션 참조를 그대로 제공한다. 모든 동작에 전달용 함수를 하나씩 덧붙이지 않는다. 공개 동작 객체와 함수 참조는 앱 인스턴스 동안 유지한다.

| 진입 동작                                                         | 처리 책임                                                                                                             |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `startTimer(duration, color)`                                     | 사용자 이벤트에서 오디오 준비를 시작하고, 현재 시각·ID를 한 번 정해 타이머 추가 액션 실행. 권한 요청을 기다리지 않음  |
| `adjustTimer(id, duration)`                                       | 최신 타이머 존재 여부 확인, 현재 시각에서 종료 시각 재계산. 0 이하는 기존 조기 종료 동작 유지                         |
| `dismissTimer(id)`                                                | 해당 ID 제거. 예약 취소는 타이머 변경을 구독하는 알림 경로에서 처리                                                   |
| `acknowledgeTimers(ids)`                                          | 화면에서 확인한 ID 중 최신 시각·목록에서도 완료인 항목만 제거. 뒤늦게 추가된 완료나 진행 중 타이머를 함께 지우지 않음 |
| `setRangeMinutes`, `setTheme`                                     | 해당 필드만 변경하고 복구용 수정 필드 기록. 오래된 설정 객체 전체로 다른 변경을 덮어쓰지 않음                         |
| `openSettings`, `closeSettings`                                   | 화면 영역 변경. DOM 대화상자·초점 처리는 컴포넌트가 반영                                                              |
| `requestNotifications`, `disableNotifications`                    | 공통 권한·예약 경로 호출. 결과와 사용자 선택은 명시적인 store 액션으로 반영                                           |
| `retryTimerStorage`, `retrySettingsStorage`, `retryNotifications` | 실패한 작업을 실행 계층에서 다시 수행하고 결과 반영                                                                   |
| `enableAudio`, `testAudio`, `sendTestNotification`                | 오디오 활성화와 테스트 동작. 실제 타이머·완료 목록을 변경하지 않으며 오디오는 사용자 이벤트에서 직접 준비             |
| `refreshNotificationPermission`, `deferNotificationPrompt`        | 요청 창 없는 권한 재확인 또는 이번 실행의 안내 종료. 알림 기능 단계에서 공개 계약에 추가                              |

ID 생성·현재 시각 취득은 사용자 동작 경계에 둔다. 상태 변경 액션은 전달받은 값으로 갱신하여 단위 테스트에서 정확한 시각을 재현할 수 있게 한다. 기존 순수 시간·범위 함수를 재사용한다. UI, XState, 네이티브 복귀가 각자 타이머 생성·완료 공식을 재구현하지 않는다.

## 5. 앱 시작과 실행 자원의 수명

`AppStateProvider`가 store와 앱 실행 객체를 한 번 생성하고, 루트의 연결 훅이 실행 객체의 시작·정리를 맡는다. 둘의 생성 과정은 외부 작업을 실행하지 않는다. `appRuntime.ts`는 담당 모듈의 생성·연결·해제와 공개 동작 참조 조립만 맡는다. 플러그인 레지스트리나 범용 실행 프레임워크를 만들지 않는다.

타이머 사용자 동작은 `timerCommands.ts`, 저장 복원·재시도는 `persistence.ts`, 권한·알림 연결은 `notificationRuntime.ts`에 둔다. `appRuntime.ts`에 타이머 계산, 복구 병합, 권한 전환, 플랫폼별 분기를 모으지 않는다. 계산·검증과 ID별 예약 처리는 기존 모듈을 재사용한다.

### 최초 복원과 재연결의 구분

| 상황                           | 저장 상태 처리                                                         | 실행 자원 처리                             |
| ------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------ |
| 새 앱 인스턴스의 최초 시작     | 타이머·설정별 `미확인` 상태에서 한 번 읽고 성공 또는 읽기 실패로 전환  | 최신 메모리 상태로 Worker·구독 연결        |
| 같은 인스턴스의 `stop → start` | 재조회·재복원하지 않음. 미저장 변경·실패·수정 필드·안내 처리 상태 유지 | 정리된 자원만 다시 연결하고 현재 시각 반영 |
| 읽기 실패의 명시적 재시도      | 저장값을 읽어 기존 규칙으로 현재 메모리 값과 병합                      | 성공한 영역의 저장 연결 활성화             |
| 쓰기 실패의 명시적 재시도      | 다시 읽지 않고 최신 메모리 값을 저장                                   | 기존 자원 유지                             |

최초 읽기 실패도 초기 시도를 마친 상태다. 재연결로 자동 재조회하지 않는다. 저장 영역의 읽기 상태를 최초 복원 여부의 기준으로 사용하고 같은 의미의 초기화 플래그를 추가하지 않는다. 실행 객체의 연결 여부·구독 핸들은 이 상태와 별도로 관리한다. 실제 다음 앱 실행은 새 store를 만들기 때문에 최초 조회를 다시 수행한다.

### 시작 순서

1. 화면은 기본 셸을 표시한다. store의 저장 상태는 `미확인`으로 시작하며 빈 저장소라고 가정하지 않는다.
2. 아직 `미확인`인 타이머·설정만 기존 읽기 함수로 읽고 도메인별 성공·실패를 반영한다. 동기 저장 읽기와 최초 테마 적용은 첫 페인트 전 연결 단계에서 처리하여 테마가 바뀌는 깜박임을 피한다.
3. 읽기에 성공한 영역의 저장 구독을 연결한다. 실패한 영역은 현재 메모리의 사용을 허용하되 원본 저장값을 덮어쓰지 않는다.
4. 현재 시각을 반영하고 기존 Worker를 시작한다. 타이머 종료 시각 목록을 전달한다. 이후 목록이 바뀔 때만 Worker 입력을 갱신한다.
5. 알림 제공 여부·권한 초기 조회와 복귀·오디오·알림 액션 구독을 연결한다. 권한 조회와 저장 읽기는 독립적으로 진행할 수 있지만 초기 안내·예약 판단은 필요한 저장 상태가 확인된 뒤에 한다.
6. 완료 목록·초기 권한 안내·설정 화면이 같은 store 상태를 읽는다. 권한 안내에서 확인할 때만 OS 요청을 호출한다.

### 수명과 재진입 규칙

- 활성 앱 인스턴스에 Worker와 각 구독은 하나씩만 존재한다. `start`·`stop`을 반복해도 구독·알림음이 누적되지 않아야 한다.
- React StrictMode의 시작 → 정리 → 재시작에서는 정리된 자원을 다시 연결한다. 한 번 실행 플래그만 남겨 Worker가 영구적으로 꺼지는 구현을 금지한다.
- 초기 조회의 진행 중 작업과 안내 처리 여부는 앱 인스턴스 기준으로 조율한다. 같은 시작 과정의 중복 호출을 합치고 실제 다음 앱 실행에서는 다시 확인한다.
- 정리 후 늦게 도착한 구독 등록 결과는 즉시 해제한다. 오래된 권한·예약 응답이 최신 사용자 선택을 덮어쓰지 않도록 실행 순서와 요청 식별을 확인한다.
- 화면을 닫거나 앱 연결을 정리하는 것은 기기 알림 사용 중지와 다르다. 예약된 네이티브 알림을 컴포넌트 unmount만으로 일괄 취소하지 않는다.
- 저장·알림 구독이 상태에 오류를 반영해도 동일 작업을 재귀적으로 호출하지 않게 한다. 구독 대상은 전체 state가 아니라 관련 데이터 참조·의미 있는 상태 변화로 한정한다.

## 6. 저장과 복구 계약

기존 `timerStorage.ts`의 키, 읽기 검증, 이전 색상·시간 범위 변환을 재사용한다. Zustand `persist`는 저장 대상 선택·이전·복원 옵션을 제공하지만 현재의 오류 복구 정책을 그대로 대신하지는 않는다. 이번에는 작은 저장 연결 모듈로 기존 계약을 유지한다. [persist 문서](https://zustand.docs.pmnd.rs/reference/integrations/persisting-store-data)

- 저장 키는 `one-slide-timer:timers`, `one-slide-timer:settings`를 유지한다. Zustand 전용 `{ state, version }` 포맷으로 감싸거나 기존 키를 삭제하지 않는다.
- 읽기 상태와 쓰기 상태를 타이머·설정별로 분리한다. 한쪽 실패가 다른 쪽의 정상 동작을 막지 않는다.
- 빈 저장소는 정상 초기값이다. 읽기·파싱·검증 실패는 미복구 상태이며 기존 값을 덮어쓰지 않는다.
- 쓰기 실패에도 메모리의 생성·조정·삭제·설정 변경은 계속 동작한다. 재시도는 최신 store 데이터를 저장한다. 이미 읽은 저장소를 다시 읽어 삭제한 타이머를 되살리지 않는다.
- 최초 읽기 실패의 복구는 기존처럼 저장된 타이머와 현재 타이머를 ID로 합치고 현재 값을 우선한다. 정상 복구 전에 만든 타이머를 유실하지 않는다.
- 설정 복구는 저장값에 사용자가 바꾼 필드만 덮는다. 범위·테마·알림 사용 선택이 같은 규칙을 따른다. 수정 필드 정보는 성공적인 복구 뒤 정리한다.
- 상태 변경과 저장 성공 표시는 구분한다. 구독 등록 전 변경을 놓치지 않도록 초기 복원·구독 연결·첫 동기화 순서를 테스트한다.
- `now`, 권한 스냅샷, 화면 선택, 안내 여부, 오류, Worker·오디오 자원은 저장하지 않는다. 타이머가 돌아가는 매 초마다 저장하지 않는다.
- 타이머 읽기 실패를 빈 목록으로 전달해 네이티브 예약을 지우지 않는다. 사용자의 명시적인 알림 X 선택에 의한 취소는 별도로 실행한다.
- 새로운 알림 설정 필드의 `null / true / false` 이전과 실패 안내는 알림 계획을 따른다. store 이전 단계에서는 기존 설정만 먼저 옮기고 권한 기능 단계에서 필드를 추가한다.

기존 `useStoredState`는 마지막 호출부 이전 후 삭제한다. React 훅과 store가 양방향 effect로 데이터를 복사하는 중간 구조를 남기지 않는다.

## 7. 시간 갱신·렌더링·XState 경계

### 시각과 애니메이션

- Worker는 계속 UI 갱신 신호만 보낸다. 수신 시 `Date.now()`를 읽어 store의 `now`를 갱신한다. 현재 초 경계 스케줄러와 실패 시 폴백을 유지한다.
- 타이머 생성·조정은 새 종료 시각과 기준 시각을 같은 상태 변경에서 반영한다. 첫 숫자 감소가 늦어졌던 회귀를 다시 만들지 않는다.
- 레일 위치·라벨 계산은 기존 순수 함수와 `useRailLayout`이 담당한다. transform 보간은 기존 `useTimerMotion`에 유지하며 매 프레임 store를 갱신하지 않는다.
- `App` 셸은 `now`와 전체 타이머 배열을 구독하지 않는다. 레일은 시각과 타이머, 상태 표시는 개수, 설정은 설정값, 안내는 필요한 오류·권한만 구독한다.
- 완료 목록은 타이머·시각에서 계산한다. 완료 알림 열림 여부와 반복 알림음 시작·정지는 `완료 개수 > 0`의 변화로 처리한다. 완료 항목 추가나 tick만으로 반복 주기를 재시작하지 않는다.

### selector 규칙

- 단일 값·안정적인 액션 참조 구독을 기본으로 한다. 여러 값을 묶거나 완료·진행 목록을 반환할 때는 참조 안정성을 검토한다.
- selector 안에서 매 호출마다 새 배열·객체를 반환한 채 기본 비교에 맡기지 않는다. 같은 요소 참조의 배열은 `useShallow`를 사용하고, 비용 있는 계산은 실제 입력값 기준으로 메모한다. 계산 결과를 별도 store 상태로 저장하지 않는다. [공식 useShallow 안내](https://zustand.docs.pmnd.rs/learn/guides/prevent-rerenders-with-use-shallow)
- 화면 변경, 권한 조회, `now` 갱신이 불필요한 저장·Worker 갱신·알림 재예약을 발생시키지 않는지 구독 호출 횟수로 확인한다.

### XState와 로컬 상태

- XState의 `idle`, `creatingTimer`, `editingTimer`, `showingTimerActions`, `adjustingTime` 및 미리보기 데이터는 이전하지 않는다.
- 기존 actor의 생성 위치를 `useRailInteraction` 내부에서 레일과 권한 안내의 공통 부모인 `App`으로 올린다. `useActorRef`로 안정적인 참조 하나를 만들고 `TimerRail`과 `NotificationPermissionPrompt`에 props로 전달한다. store에 actor를 넣거나 두 번째 actor를 만들지 않는다.
- `useRailInteraction`은 전달받은 actor의 필요한 상태를 `useSelector`로 구독하고 포인터·키보드 처리를 연결한다. XState가 확정한 생성·수정·조기 종료는 `AppActions`에 전달한다. 현재 `commitTimer`의 콜백 입력을 필요한 공개 타이머 동작으로 좁혀 레일 DOM·측정값 없이 연결한다. 기존 취소·Escape·pointercancel·편집 중 완료 처리를 유지한다.
- 레일의 최신 타이머·설정은 Zustand selector로, 사용자 동작 실행에 필요한 최신 원본은 담당 실행 모듈 내부의 store 조회로 읽는다. actor context에 타이머 목록이나 설정을 복제하지 않는다.
- 권한 안내는 같은 actor의 `idle` 여부만 `useSelector`로 구독한다. `creatingTimer`, `editingTimer`, `showingTimerActions`, `adjustingTime`에서는 안내를 보류하여 드래그·타이머 액션·시간 조정을 방해하지 않는다. `getSnapshot()`만 조회해 렌더 갱신을 기대하거나 `isIdle`을 Zustand·React state에 복사하지 않는다. 드래그 미리보기의 변경은 레일에서 구독하며 부모 `App`과 권한 안내가 전체 snapshot을 구독하지 않는다.
- 권한 안내는 레일이 `idle`이고 설정·완료 알림이 닫혀 있으며 안내 대상일 때만 표시한다. 드롭·취소·메뉴 닫기·시간 조정 종료로 `idle`에 돌아오면 최신 조건을 다시 판단한다. 보류는 안내를 처리한 것으로 기록하지 않는다. 권한 안내가 열린 중에 완료 알림이 필요해져도 완료 알림을 우선하고, 조건이 해소된 뒤 미처리 안내를 다시 판단한다. DOM dialog·초점 처리는 해당 화면이 맡는다.
- `TimerAdjustment` 입력값, DOM dialog 상태·초점, ResizeObserver 측정값, 애니메이션 핸들은 그대로 로컬에 둔다. 전체 상태 관리 계획에서 소유자를 명확히 지정한 예외다.

## 8. 알림 계획과의 통합

- 기존 알림 계획의 `공통 훅이 권한 상태를 보관`하는 부분을 `Zustand 알림 영역이 보관`으로 대체한다. 연결 훅은 상태를 복제하지 않고 외부 작업의 시작·정리만 맡는다.
- 앱 시작 조회 → 필요한 경우 앱 안내 팝업 → 확인 → OS 권한 요청 흐름을 유지한다. 타이머 생성 자체에는 권한 요청을 연결하지 않는다.
- `notificationRuntime`이 권한 어댑터의 조회·요청과 그 결과의 store 반영을 유일하게 담당한다. 초기 조회·앱 복귀·설정 재확인·예약 직전 재확인은 같은 조회 경로를 사용하고, 팝업과 설정 O 선택은 같은 요청 동작을 호출한다. 조회·요청 중복 방지와 최신 결과 검증도 이 모듈에 둔다.
- O/X는 제공 여부·실제 권한·사용자 선택으로 계산한다. 권한을 기다리며 타이머를 삭제·조정하거나 사용을 껐을 때는 현재 store를 다시 확인한다.
- `syncNotifications`는 권한 어댑터를 직접 조회·요청하거나 자체 권한 캐시를 만들지 않는다. 예약 직전에는 `notificationRuntime`이 제공하는 확인 콜백을 사용한다. 콜백은 공통 조회 결과를 store에 반영한 뒤 최신 사용자 선택을 확인하고, 동기화 모듈은 대기 후 최신 대상·종료 시각을 다시 확인한다. 조회 경로가 동기화 모듈을 다시 호출하며 순환 대기하지 않게 한다.
- 기존 ID별 예약 직렬화·취소 실패 재시도는 `syncNotifications`에 유지한다. 이 모듈에는 예약·취소 기능과 위 확인 콜백만 전달하며 권한 변경 액션이나 전체 store를 전달하지 않는다. 작업 큐는 내부에 두고 UI가 필요한 처리 상태와 오류만 알림 영역에 반영한다.
- 예약 전 재조회에서 거부가 확인되면 설정 화면도 같은 결과로 X를 표시한다. 조회 실패는 거부로 덮지 않고 미확인·오류로 반영하며 새 예약을 보류한다. 권한 조회 상태만 바뀌었다고 이미 반영한 같은 대상의 예약 작업을 다시 쌓지 않는다. 보류된 목표는 조회 성공·사용 켜기·명시적 재시도에서 다시 처리한다.
- 예약 판단에서 권한 미확인·조회 실패를 명시적 X나 빈 목표 목록으로 바꾸지 않는다. 기존의 일괄 `취소 → 권한 확인 → 예약` 순서를 그대로 재사용하지 않고, 변경 없는 예약 보존·명시적 취소·종료 시각 변경에 따른 교체를 구분한다. 단순 재확인 실패에는 기존 유효 예약을 유지하고, 조기 종료·완료 확인·X 선택에 따른 취소는 권한 확인 성공을 요구하지 않는다.
- 종료 시각이 바뀐 예약은 권한 응답을 기다리지 않고 이전 예약을 먼저 취소한다. 새 예약만 공통 권한 확인과 최신 의도 검증 뒤 실행한다. 권한 Promise는 ID별 예약·취소 큐를 점유하지 않는다. 조회 실패·거부 시에도 이미 무효인 이전 종료 시각의 예약은 취소하고 새 예약을 보류한다. 취소 실패 시 교체를 진행하지 않으며, 새 예약 실패 시 이전 시각으로 복원하지 않고 최신 목표의 재시도를 남긴다. 세부 처리 순서와 실패 복구는 [알림 계획의 예약 처리 계약](notification-permissions-plan.md#예약-보존취소교체의-처리-순서)을 따른다.
- 오디오 모듈의 실제 상태 변경을 앱 실행 계층에서 한 번 구독해 `audioReady`를 갱신한다. 첫 사용자 조작에서 `prepareAlertAudio`를 직접 호출하는 제약을 유지한다.
- 기기 알림 X·권한 거부·미지원 환경은 앱 내부 반복 알림음과 타이머 사용을 막지 않는다. 2026-09-28 범위를 정정하여 웹 시스템 알림과 알림 표시·클릭 전용 service worker를 포함한다. 권한은 기존 Zustand 영역과 요청 경로를 공유하고, 완료 전달은 store의 타이머·시각을 구독한다. 웹 어댑터에 타이머 원본이나 미래 예약 시계를 복제하지 않는다. 서버 Web Push와 offline cache는 제외한다.

## 9. 파일별 이전 방향과 구현 결과

아래는 책임별 목표다. 일대일 전달만 하는 래퍼는 만들지 않고 기존 파일을 이동·대체한다. 타입·selector는 사용 영역에 함께 두고 공통으로 쓰는 부분만 추출한다.

| 현재 위치                                                  | 이전 방향                                                                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `app/useTimers.ts`                                         | 타이머 state/action은 `app/state/timerState.ts`, Worker·사용자 동작은 앱 실행 계층으로 이전 후 기존 훅 삭제              |
| `app/useSettings.ts`                                       | 설정 state/action·수정 필드 추적은 `app/state/settingsState.ts`, 테마 DOM 적용은 루트의 연결 효과로 이전 후 기존 훅 삭제 |
| `app/useStoredState.ts`                                    | 상태·복구 메타데이터는 각 store 영역, 읽기·쓰기·구독은 `app/persistence.ts`로 이전 후 삭제                               |
| `app/useTimerNotifications.ts`                             | 화면 상태는 `app/state/notificationState.ts`, 외부 작업은 `app/notificationRuntime.ts`로 대체                            |
| `app/App.tsx`, `main.tsx`                                  | `app/AppStateProvider.tsx`에서 store·실행 객체를 연결하고 App은 actor 연결과 화면 조립 담당                              |
| 신규 `app/state/appStore.ts`                               | 세 상태 영역과 작은 화면 영역 조립, `createAppStore` 제공                                                                |
| 신규 `app/timerCommands.ts`                                | 공개 타이머 동작의 시각·ID·오디오 준비와 내부 타이머 액션 연결. 시간 계산은 기존 순수 함수 재사용                        |
| 신규 `app/appRuntime.ts`                                   | 담당 모듈과 Worker의 연결·해제, `AppActions` 참조 조립만 담당. 타이머·복구·권한 정책은 각 담당 모듈에 유지               |
| `app/App.tsx`, `features/timer-rail/useRailInteraction.ts` | App에서 actor 하나를 생성해 레일·권한 안내에 전달. 조작 훅의 actor 생성 제거, 각 소비자는 필요한 snapshot만 구독         |
| `app/AppNotices.tsx`                                       | 훅 반환 타입 의존 제거. 필요한 상태를 구독하고 명시적인 재시도 동작 호출                                                 |
| 설정·완료·레일의 화면 진입 컴포넌트                        | 필요한 selector·동작만 구독. RangeSettings·ThemeSettings·TimerPin 등 작은 표현 컴포넌트는 props 유지                     |
| `domain/timer/*`, `workers/*`, `platform/notifications/*`  | 기존 계산·검증·시각·플랫폼 역할 유지. 필요한 연결 계약만 변경                                                            |

새 store에서 옛 훅을 호출하거나 옛 훅의 결과를 store에 복사하는 방식은 사용하지 않는다. 기존 이름의 훅을 남길 경우에도 실제 필요한 selector 묶음일 때만 허용하고 별도 상태 소유나 효과를 남기지 않는다.

## 10. 적용 순서

### 1단계 — 계약과 검증 기준 고정

- 기존 테스트와 저장값·사용자 동작을 기준으로 회귀 목록을 만든다. 현재 동작의 오류를 발견하면 상태 이전과 구분해서 기록한다.
- Zustand 의존성, 독립 store 생성, 고정 인스턴스 전달, 필요한 상태·액션 타입을 추가한다. 이 단계의 미연결 store는 운영 상태의 두 번째 소유자로 사용하지 않는다.
- 독립 인스턴스 두 개의 격리와 순수 액션을 검사한다. import·생성만으로 외부 작업이 시작되지 않는지 확인한다.
- 상태 전용 `AppState`, 공개 `AppActions`, 내부 변경 액션의 타입·export를 확정한다. 화면에서 내부 액션과 원본 store를 얻지 못하는 호출 구조를 검사한다.

### 2단계 — 설정과 앱 화면 전체 이전

- 시간 범위·테마·메인/설정 선택·설정 저장 복구를 한 묶음으로 이전한다. 테마 반영, meta 색상, dialog·초점 동작도 연결한다.
- settings selector와 필드별 액션으로 화면을 바꾸고 기존 `useSettings`를 제거한다.
- 범위 경계·키보드·테마·재실행·읽기/쓰기 실패 복구 검사를 통과시킨다. 이 단계부터 설정의 활성 소유자는 store 하나다.
- 최초 복원과 연결 수명을 분리하고, 저장 실패 중 설정 변경 후 같은 인스턴스를 재연결해도 값·수정 필드·복구 안내가 유지되는지 검사한다.

### 3단계 — 타이머와 시간 갱신 전체 이전

- 타이머 원본·시각·저장 복구·사용자 동작·Worker 수명을 함께 이전한다. 기존 알림 연결은 이 단계 동안 최신 store 값을 입력받는 기존 경로 하나로 유지한다.
- 생성·조정·조기 종료·완료 확인, 레일 selector, XState 확정 연결을 이전한다. `useTimers`와 마지막 `useStoredState` 호출부를 제거한다.
- actor 생성은 App으로 올리고 레일은 전달받은 참조를 사용한다. 미리보기의 변경이 App을 다시 렌더하지 않는지와 모든 확정 경로가 공개 동작을 사용하는지 확인한다.
- 초 경계, Worker 폴백, 애니메이션, 저장 실패 중 생성·수정·삭제 후 복구, 완료 확인 범위를 검사한다.
- 쓰기 실패 중 생성·수정·조기 종료 뒤 `stop → start`를 거쳐도 저장소를 재조회하지 않고 메모리 상태와 실패 안내가 유지되는지 확인한다.

### 4단계 — 기존 알림 상태와 실행 수명 이전

- 현재 알림 오류·오디오 상태를 알림 영역으로 옮기고 `useTimerNotifications`의 외부 작업을 실행 모듈로 대체한다.
- 구독·Worker·반복음의 루트 연결을 완성하고 StrictMode·재시작·늦은 응답의 정리를 검사한다. 이 단계에서는 새 권한 UI를 추가하지 않고 기존 기능 회귀를 먼저 확인한다.

### 5단계 — 구독 범위와 남은 결합 정리

- App의 시각·전체 객체 구독, 반환 객체 통째 전달, 불필요한 중간 훅과 구독을 제거한다.
- 변경 없는 tick에서 설정·앱 셸이 상태 때문에 다시 렌더되지 않는지, 저장·예약·Worker 입력이 불필요하게 실행되지 않는지 검사한다.
- 여기까지를 기존 기능의 Zustand 이전 완료 지점으로 삼고 전체 `verify`, `verify:browser`를 통과시킨다.

### 6단계 — 새 권한 기능을 store 위에 구현

- 알림 계획의 제공 여부·권한 API·초기 안내·O/X·예약 취소 복구·테스트 알림을 적용한다.
- 권한 조회·요청·store 반영을 `notificationRuntime`으로 모으고 예약 전 재확인도 같은 경로에 연결한다. 다른 모듈의 직접 권한 조회와 별도 권한 캐시를 제거한다.
- 예약 보존·명시적 취소·교체를 구분하여 조회 실패가 유효 예약을 지우지 않도록 한다. 조기 종료·X 선택은 권한 오류에도 취소하고, 시간 조정 후에는 이전 시각의 예약 정리와 최신 목표 재시도를 검사한다.
- 알림 사용 선택의 저장 이전, 앱 복귀, 초기 안내와 완료 알림의 우선순위를 연결한다. 기존 훅 상태를 다시 도입하지 않는다.
- 권한 안내가 레일과 동일한 actor의 `idle` 여부를 구독하도록 연결한다. 생성·편집 드래그, 타이머 액션, 시간 조정 중 초기 조회 완료 → 안내 보류 → `idle` 복귀 → 최신 조건으로 안내, 안내 중 완료 발생의 우선순위를 검사한다.
- 알림 계획의 구현 순서 중 상태·저장·앱 조립 부분은 앞 단계 결과를 재사용하고 중복 구현하지 않는다.

### 7단계 — 회귀 검사와 코드 리뷰

- 기존 테스트를 유지하고 소유권·수명·저장·selector·권한 경합 검사를 보강한다. 내부 구현을 그대로 따라가는 테스트보다 사용자 동작과 결과를 검사한다.
- 대표 오류를 임시 주입하여 새 검사가 실제로 실패하는지 확인한다. 리뷰에서 발견한 결함을 수정하고 관련 검사를 다시 실행한다.

### 8단계 — 실제 환경 검증과 문서 마무리

- iOS 실기기의 시작 권한 흐름·복귀·종료 후 예약·실제 소리와 알림을 확인한다. 브라우저 자동 검사와 구분해 결과를 기록한다.
- 상태 소유권 표, 삭제·이전된 파일, 제품 스펙과 진행 기록을 실제 결과에 맞춘다. 기기 검증이 남으면 구현 완료와 검증 미완료를 나눠 보고한다.

각 단계는 실행 가능한 상태로 끝낸다. 동일 영역의 두 상태 소유자를 동기화해 놓고 다음 단계로 넘기지 않는다. 커밋·push는 별도 사용자 요청 시 수행한다.

## 11. 검증과 완료 기준

| 검증 영역   | 반드시 잡아야 할 회귀                                                                                    |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| 소유권·격리 | 훅을 두 번 써서 별도 목록 생성, 앱/테스트 간 singleton 상태 누출, React와 Zustand의 양방향 복사          |
| 저장        | 읽기 실패 원본 덮어쓰기, 부분 설정 유실, 실패 후 최신 값 대신 과거 값 저장, 시각 tick마다 쓰기           |
| 시간·레일   | 첫 숫자 감소 지연, stale 종료 시각, 범위 변경 시 endAt 수정, 취소된 드래그 확정, 완료된 타이머 편집 잔존 |
| 완료·오디오 | 확인 시 진행 중 타이머 삭제, 추가 완료마다 반복음 재시작, X 선택이 앱 내부 알림음까지 끔                 |
| 실행 수명   | StrictMode 이후 Worker 정지 또는 중복 실행, 해제 뒤 이벤트 반영, 앱 unmount만으로 네이티브 예약 취소     |
| selector    | 새 snapshot 참조의 무한 렌더, 설정이 tick을 구독, 무관한 변경에 알림 재예약·저장 실행                    |
| 권한        | 초기 조회만으로 OS 팝업, 안내 확인/설정 O의 중복 요청, 늦은 허용 응답이 사용자 X 선택을 덮어씀           |
| UI          | 네 테마, 5분~12시간 범위, 터치·키보드·초점, 확대·하단 안전 영역·동작 줄이기 회귀                         |

- store 테스트는 실제 Zustand 인스턴스와 액션을 사용한다. 저장·Worker·OS 같은 외부 경계만 제어한다.
- 실행 수명 검사는 시작·중복 시작·정리·재시작 후 활성 자원 수와 작업 호출을 확인한다. 시각·권한 경합에는 제어된 시간과 미해결 Promise를 사용한다.
- 재연결 검사는 초기 읽기 호출 수가 늘지 않고, 미저장 타이머·설정·수정 필드와 실패 상태가 유지되는지 확인한다. 읽기 실패 뒤에는 재연결이 아닌 명시적인 재시도만 복원을 시도해야 한다.
- 공개 진입점의 타입 검사에서 내부 복원·권한 반영 액션과 `setState`에 접근할 수 없어야 한다. 사용자 흐름 검사는 공개 동작부터 오디오 준비·시각 갱신·저장 연결까지 확인한다.
- actor 공유 검사는 생성·편집 드래그, 타이머 액션, 시간 조정 중 늦은 권한 조회 결과를 재현한다. 드롭·취소·메뉴 닫기·조정 종료 전에는 안내가 없고 `idle` 복귀 후 조건을 만족할 때만 표시되며, 안내 중 완료는 우선 처리되어야 한다. 드래그 미리보기만 바뀔 때 권한 안내의 `idle` 구독값이 바뀌지 않는지도 확인한다.
- 예약 전 권한 재조회가 거부·오류를 반환하면 store와 설정 화면도 같은 상태를 보여야 한다. 조회·요청 경합에서 오래된 응답이 최신 허용·사용 중지 선택을 덮지 않고, 조회 결과 반영이 중복 예약이나 순환 대기를 만들지 않는지 검사한다.
- 이미 예약된 타이머의 단순 재조회 실패에는 취소·재예약이 없어야 한다. 같은 실패 상태에서 조기 종료·완료 확인·X 선택은 취소되어야 하며, 종료 시각 변경은 이전 예약을 정리하고 새 예약을 보류해야 한다. 취소 실패 후 교체 중단, 새 예약 실패 후 최신 목표 재시도, 대기 중 추가 조정·X 선택도 검사한다.
- 기존 `storage-recovery`, `timer-tick`, `timer-worker`, `timer-alert`, `rail-interaction`, `rail-touch`, 설정·접근성·모션 브라우저 검사를 유지한다. 테스트에서 store 값을 직접 바꿔 사용자 흐름을 우회하지 않는다.
- 무관한 tick에서 쓰기·재예약이 없는지와 현재 완료 여부 전환을 검사한다. 렌더 횟수 검사는 필요한 구독 경계에 한정하고 React 개발 모드의 절대 횟수를 고정하지 않는다.
- Node 24에서 `npm run verify`, `npm run verify:browser`를 실행한다. 대표 결함 주입은 저장 읽기 실패 보호 제거, 늦은 응답 검증 제거, tick의 전체 상태 구독 중 최소 두 가지로 수행한다.
- 실제 iPhone의 잠금·백그라운드·무음·집중 모드, VoiceOver와 시스템 권한 창은 기기·OS·빌드와 함께 기록한다. API mock의 통과를 실제 전달 보장으로 표현하지 않는다.

완료 시 공유 상태는 지정된 Zustand 영역 하나에만 존재해야 한다. XState·로컬 상태·플랫폼 자원의 예외는 위 소유권 표와 일치해야 하며, 기존 저장 데이터와 사용자 동작은 유지되어야 한다. 코드를 읽을 때 **어디에서 읽고, 어떤 동작으로 바뀌며, 누가 외부 작업을 실행하는지**를 한 경로로 추적할 수 있어야 한다.

## 12. 구현 결과 (2026-09-18)

- 1~7단계 구현과 회귀 검사를 완료했다. 공유 상태는 앱별 `createAppStore` 하나에 있고, 화면 진입점은 `useAppStore`·`useAppActions`다. 기존 상태 훅 네 개를 삭제했다.
- 권한 실행 모듈은 `notificationRuntime.ts`와 `notificationPermission.ts`로 나눴다. 전자는 수명·예약·오디오를 연결하고 후자는 권한 조회·요청·최신 결과 검증을 전담한다. 별도 권한 캐시는 없다.
- 기기 예약을 처음 읽기 전에는 새 예약을 보류한다. 기기 예약 조회와 권한 조회는 병행하므로 X·삭제·조정에 따른 취소는 권한 응답을 기다리지 않는다.
- 실제 예약 조회의 오래된 응답은 OS 예약·취소 작업의 변경 이력으로 판별한다. 사용자 선택 변경만으로 실제 예약 결과를 버리지 않고 최신 목표와 대조한다.
- 설정 읽기 실패의 기본값은 사용 동의로 취급하지 않는다. 같은 실행에서 명시적으로 O를 선택한 값은 메모리에서 적용하며 읽기 복구 시 보존한다.
- iOS 플러그인 동기화는 완료했다. 8단계의 실기기 알림 전달·VoiceOver·잠금·백그라운드 검증은 기기 연결 환경에서 남아 있다. 자동 검사와 리뷰 결과는 [진행 기록](progress.md)을 따른다.

### 알림 전달 경계 보완 (2026-09-28)

- `notificationRuntime`은 공통 권한 경로·store 구독·오디오 연결만 담당한다. 웹과 iOS의 전달 방식을 판별하지 않는다.
- store selector가 타이머·현재 시각·목록 완전성·전달 정책을 하나의 입력으로 만든다. 권한과 사용자 선택의 소유자는 계속 Zustand이며 adapter에는 실행 기록만 둔다.
- `platform/notifications`가 예약 복원·동기화 또는 완료 목록 병합·정리를 소유한다. 앱은 내부 driver·예약 체크포인트·비동기 유효성 검사를 알 필요가 없다. ESLint로 앱·화면의 내부 구현 import를 막는다.
- 권한 보류와 명시적 X, 읽기 실패와 빈 저장소를 구분한다. 재연결은 과거 비동기 작업을 무효화하되 성공한 웹 전달 기록과 기존 네이티브 예약을 유지한다.
